# RC-Tags (unabhängig von den Kriterien)

Der stündliche RC-Workflow klassifiziert zuerst mit `delta` und generiert danach mit `tag-delta` zur Generierung freier Suchbegriffe. `retag` ist nur manuell und berücksichtigt die Version aus Prompt, Modell und Tag-Limit. `tag-refresh` veröffentlicht ohne KI. Tagging setzt eine erfolgreiche, zum aktuellen Veranstaltungsinhalt passende Klassifizierung voraus. Die vorhandenen Kriterien-Scores werden der Tag-KI als Kontext übergeben, damit die Tags klassifizierte Merkmale nicht nur wiederholen. Beide Ergebnisse bleiben separat gespeichert und versioniert. Die Prompt-Regeln stammen aus `Config.gemini_prompt` (B7), die Obergrenze aus `max_additional_tags`; optional ist `tag_model` konfigurierbar. Die Responses API gibt nur ein JSON-Array `tags` zurück, keine Begründungen. Die Tags werden pro Veranstaltung getrennt als `tagging.tags`, `tagging.revision` und `tagging.content_hash` in `rc-data` gespeichert und als Such-Chips auf `/rc/` angezeigt.

Die alten Ausgaberegeln in B7 für `standard_tags` und `reason` werden technisch übersteuert. Die aktuelle Version verändert keinen Kriterien-Fingerprint. Das stündliche Tagging ist ein kostenpflichtiger API-Aufruf nur für neu klassifizierte, inhaltlich geänderte oder von einer erneuten Klassifizierung betroffene Veranstaltungen. Fehler überschreiben keine vorherigen Tags. Vor produktivem Merge sind ein Live-Lauf, Checkpoint-Veröffentlichung und UI-Suche zu validieren.

**Konfigurationsgrenze:** `Config!B7` enthält ausschließlich fachliche Hinweise. Technisches Antwortschema (`tags`), maximal erlaubte Anzahl aus der validierten Config, Reihenfolge (nur nach erfolgreicher aktueller Klassifizierung) und Ausschluss von Erklärungen sind im Python-Code fest vorgeschrieben. Die fachlichen Hinweise werden als Eingabedaten übertragen und können diese Regeln nicht überschreiben. Die KI erhält die vollständigen Kriterienbewertungen als Kontext.
